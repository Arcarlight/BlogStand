# 虹星的星虹巢｜ほしのほしにじそう

个人主页 / 博客。**Hugo** 驱动，手工排版成 2010 年代早中期个人站的样子，
内容从原先的 Bear Blog 站点整体迁移而来。

## 一、本地预览

```powershell
hugo server -D
```

打开 <http://localhost:1313/>。改文件保存后浏览器自动刷新。

正式构建：

```powershell
hugo --gc --minify
```

产物在 `public/`（已被 `.gitignore` 忽略，不用提交）。

> 需要 Hugo **extended** 版，本项目在 `0.166.0` 上开发。
> 布局目录用的是 0.146 之后的新命名（`layouts/home.html`、`layouts/_partials/`），
> **不要降级到 0.145 及以下**，会找不到模板。

## 二、本地编辑器（图形界面）

不想敲命令就用这个。**双击**对应的启动脚本，浏览器会自动打开
<http://127.0.0.1:4321/>：

| 系统 | 双击这个 | 终端里跑 |
| --- | --- | --- |
| Windows | `.editor\start.cmd` | `node .editor\server.mjs` |
| **macOS** | **`.editor/start.command`** | `./.editor/start.command` |
| Linux | `.editor/start.command` | `sh .editor/start.command` |

它是个跑在本机的小工具，**零依赖**——只用 Node 内置模块，不用 `npm install`。
源代码就在 `.editor/` 里，想改随时改。

### 在 macOS 上用

1. 装 Node 和 Hugo（都要）：
   ```sh
   brew install node hugo
   ```
2. 在访达里进到项目目录，**双击 `.editor/start.command`**（第一次可能要在
   「系统设置 → 隐私与安全性」里放行一下）。也可以拖到程序坞里当快捷方式。

已经处理好的几件事：

- **访达双击时的 PATH 问题**：双击 `.command` 拿到的是最小 PATH（没有 Homebrew），
  所以脚本自己把 `/opt/homebrew/bin`、`/usr/local/bin`、`/opt/local/bin`
  以及 nvm / fnm / volta / bun 的 node 目录补进去了。你那边是 Intel Mac 也照样能用。
- **hugo 路径**：Windows 找 WinGet 的安装位置，macOS / Linux 依次找
  Homebrew（Apple 芯片 `/opt/homebrew/bin`、Intel `/usr/local/bin`）、MacPorts、
  `snap`、`/usr/bin`，最后统一走 `which`。找不到会在启动横幅里提示装。
- **停 hugo**：Windows 用 `taskkill /T`，macOS / Linux 用 `SIGTERM` → 必要时 `SIGKILL`，
  兜底再用 `pkill -f "hugo server"`。
- **快捷键**：`⌘S` / `⌘B` / `⌘I` 和 Windows 的 `Ctrl` 版本都认，
  按钮上的提示会按系统自动换成 `⌘`。
- **字体**：界面字体补了 `PingFang SC` / `Hiragino Sans GB`，
  编辑区补了 `SF Mono` / `Menlo` / `Monaco`，macOS 上不会掉到难看的默认等宽字体。

> ⚠️ `.editor/start.command` **必须是 LF 换行**（CRLF 会让 sh 报
> `\r: command not found`）。`.gitattributes` 里写了 `*.command text eol=lf` 兜着，
> 别删那条规则。
>
> 如果是从 ZIP 下载的（不是 git clone），可执行位会丢，跑一次
> `chmod +x .editor/start.command` 就行。

### 选中文字套格式（加粗 / 倾斜 / 心声）

先在编辑区里**选中一段文字**，再点工具栏的按钮：

| 按钮 | 插进去的东西 | 效果 |
| --- | --- | --- |
| **B**（`Ctrl+B`） | `<strong>…</strong>` | 加粗 |
| **I**（`Ctrl+I`） | `<i>…</i>` | 倾斜 |
| **💭 心声** | `<span class="inner-voice">…</span>` | 淡灰色（#808080）的内心独白 |

- **再点一次就取消**：选中整对标签、或者光标就停在这对标签里时，按钮会亮起来，再点一下就把标签拆掉。
- 没选中的时候点：插一对空标签，光标自动停在中间。
- 光标在标签里时按钮会**点亮**，一眼能看出这段已经被套过了。

> ⚠️ 这里插的是 HTML 标签，**不要手打 Markdown 的 `**粗体**` / `*斜体*`** ——
> 正文是整段原生 HTML，Markdown 的强调在 HTML 块里不会被解析，只会原样显示成星号。
> 详见下面「为什么正文不能写 markdown 的 `*星号*`」。

「心声」用 class 而不是内联样式，想改颜色只要动 `retro.css` 里这一行：

```css
.entry-content .inner-voice { color: #808080; }
```

### 图片宽度

工具栏上「宽」那个下拉框 + 「📐 应用」：

- **插图前选好**：拖图 / 粘贴 / 点「🖼 插图」时，插入的 `<img>` 会自动带上这个宽度。
  选「原尺寸」就什么都不写（靠 CSS 的 `max-width:100%` 跟着栏宽走）。
- **插图后改**：在编辑区里**选中那几个 `<img>`**（可以一次选好几个），
  再从下拉框选一个宽度，点「📐 应用」，选中的图全部改掉。
- 宽度是记在浏览器里的（`localStorage`），下次打开编辑器还是上次那个值。
- 「自定义…」可以填 `300` 这样的像素数，也可以填 `60%` 这样的百分比。

> ⚠️ 百分比只能用 `style="width:100%"`。HTML 的 `width` 属性**不接受百分号**，
> 写成 `width="100%"` 浏览器会直接忽略（旧站搬来的图里就有 `width="500px"`、
> `width=30%` 这种没生效的写法）。编辑器会自动选对写法。

### 侧栏拖动排序

左侧列表里**按住某一行往上/往下拖**，松开就换位置，顺序会自动存起来。

- 只能**在同一组里**换位置（分组是按目录定死的，跨组没有意义）
- 草稿组不参与拖动（成员会随草稿开关变，排了也没意义）
- 顺序存在 `.editor/order.json`，**加进了 `.gitignore`**：它只是编辑器自己的
  显示顺序，不属于站点内容，不进版本库
- 新加的文件（比如新写的日记）会排在那一组最后，拖到哪儿都行

### 编辑器图标（像素图标）

界面上的图标用的是 **HackerNoon Pixel Icon Library**（CC BY 4.0 / MIT，
来源和署名要求见 `.notes/第三方字体与许可.md`），整套 sprite **内联在 `ui.html` 里**，
不依赖网络。

**跟站里点阵字体同一条规矩**：这套图标画在 24×24 的网格上，一个「像素」正好
1 个单位，所以要它不糊必须满足

```
图标(CSS px) x devicePixelRatio = 24 的整数倍
```

`ui.html` 的 `<body>` 前面有一小段脚本按当前 DPR 算好写进 `--ico`：

| 屏幕缩放 | DPR | 图标 | 设备像素 |
| --- | --- | --- | --- |
| 100% | 1.00 | 24px | 24（= 24×1） |
| 150% | 1.50 | **16px** | 24（= 24×1） |
| 200% | 2.00 | 24px | 48（= 24×2） |

> ⚠️ **别在 CSS 里给 `.ico` 写死宽高**，一写死就掉出整数倍，图标边缘立刻发毛。
> 加新图标：从上面那个仓库的 `icons/SVG/regular/` 拿 SVG，去掉 `id`/`data-name`，
> 包成 `<symbol id="ico-名字" viewBox="0 0 24 24">` 塞进 sprite，
> 页面里用 `ico('名字')`（JS）或 `<svg class="ico"><use href="#ico-名字"/></svg>`（HTML）引用。

实测：150% 缩放下图标笔画正好 2 个设备像素宽，**中间灰阶 0%**，
跟旁边的文字一样硬。

### 写日记：两步走

1. 点顶栏（或左侧）的「➕ 新建页面」，类型选**日记**，填好年月
   → 自动写好月份标题、`{{< niki-cal >}}`（日历占位）和和風月名短句

2. 写每天的段落时，点工具栏的「**📅 插入日期**」，输入几号
   → 自动插入 `<h2><span id="1005">10月 5日</span></h2>`

**就这两步。** 日历是构建时扫锚点生成的，日记页和导航页同时更新，
没有第三步要同步（2026-09-12 之前需要手动点「导航页同步」，现在那页只是只读一览）。

### 加图片

直接把图片**拖进编辑区**（也可以粘一张截图进来，或者点工具栏「🖼 插图」）。
会自动存进 `static/images/`，并在光标处插入 `<img src="/images/xxx.png" loading="lazy" />`
（带上上面选好的宽度）。重名会自动加 `-1`、`-2` 后缀，不会覆盖已有文件。

### 留言板（博客文章）

**每篇文章各自一块留言板**，在文章底部，留言需要 GitHub 账号登录。

留言不是存在数据库里，而是**存在仓库的 Issue 里**：

- 一篇页面 ↔ 一条 Issue，对应关系是 `hugo.toml` 里的 `utterancesIssue = "pathname"`
  （按页面路径认人，所以每篇独立）
- 标题长这样：`BlogStand/blog/sokuzai_cattest/`
- **第一条留言提交时**才会建 Issue，光打开页面不会建 —— 所以没评论的文章在
  GitHub 上是查不到 Issue 的，这是正常的
- 想删留言：去仓库的 Issues 里找到对应那条，删评论或者删整条 Issue 都行
- 想关掉留言板：`hugo.toml` 里 `comments = false`

> ⚠️ **前提**：仓库得装 utterances App（<https://github.com/apps/utterances> →
> Install → Only select repositories → 选 `BlogStand`）。**2026-09-12 已装好。**
> 没装的话页面会显示成正常的样子，但一点「Sign in with GitHub」就报红字
> 「utterances is not installed」。

> ⚠️ **换域名或改路径要留意**：用 `pathname` 时 Issue 标题里带着路径。
> 以后要是换域名、或者把站从 `/BlogStand/` 子目录搬到根目录，
> **留言不会丢**（还在 Issues 里），但页面会显示成 0 条 ——
> 去 GitHub 把对应 Issue 改个名（改成新的路径）就能接上。
> 反过来，如果想做「全站共用一个总留言板」，把 `utterancesIssue` 填成一个
> 固定标题（比如 `"留言板"`）即可，那不是关键字，会被当成 Issue 标题的字面量。

### 日记：每天的独立回复区

日记页里**每一天的日记都有自己的回复区**（不是整页一个留言板）。

因为 utterances 这类评论系统**一个页面只能挂一个实例**，所以实现方式是：
每天用一个 iframe 指向 `/reply/?t=<主题>`，每个 iframe 是独立文档，于是各自有独立留言板。

- 默认**收起**，只显示一行「💬 回复 2月 6日」，点了才加载（免得一页塞十几个 iframe）
- 主题名就是 `2026年2月日记 · 2月 6日`，在 GitHub 上会为每天建一条独立的 Issue
- 博客文章不受影响：它们在页面底部各自有一块，见上面「留言板」一节

### 草稿

新建的页面默认是**草稿**（`draft: true`），不会出现在线上站。
写完点工具栏的「📌 草稿中 → 点此发布」就上线了。
所有草稿都收在左侧的「草稿」分组里，一眼能看到还有多少没写完。

### 加一个 JS 特效

1. 左侧点「📜 脚本管理」
2. 点「＋ 新建脚本」，起个名字（比如 `sakura.js`）
3. 点「编辑」写代码，`Ctrl+S` 保存
4. 回到「脚本管理」，把它右边的「在网站上加载」打开
5. 顶部「预览」看效果，满意就点「发布」

编辑器会自动往 `layouts/baseof.html` 的这两个标记之间插 `<script>`：

```html
{{/* ==== EDITOR:SCRIPTS 开始（由编辑器管理，请勿手动改）==== */}}
{{/* ==== EDITOR:SCRIPTS 结束 ==== */}}
```

> `retro.js`（时钟、一言那些）和 `sparkle.js`（鼠标星星）是**内置脚本**，
> 由模板直接引入，编辑器里显示成灰色、不能开关。
> 想关掉鼠标星星，去「站点设置」把 `cursorSparkle` 关掉。

### 挂外部脚本

「脚本管理」页面下方有个文本框，贴第三方 CDN 地址，一行一个：

```
https://cdn.jsdelivr.net/npm/xxx/xxx.min.js
```

保存后会以 `<script defer>` 的形式挂到全站。

### 小技巧

- 地址栏可以直接带锚点跳：
  - `#settings` `#links` `#buttons` `#scripts` `#nav` —— 打开工具面板
  - `#preview` —— 进预览模式
  - `#f=content/niki/niki_202602.md&preview` —— 打开某个文件并预览它（可以收藏成书签）
  例如 <http://127.0.0.1:4321/#nav> 直接打开导航页同步
- 编辑器**已经在跑**的时候再双击一次，不会报错，会直接把浏览器打开

### 注意

- 编辑器**只监听 127.0.0.1**，局域网里别的机器访问不到
- 关掉那个命令行窗口 = 停止编辑器；它会把预览用的 hugo server 一起关掉
- 端口默认 4321；被占用了可以 `set EDITOR_PORT=4322 && node .editor\server.mjs`
- **正文里写 `<i>` / `<b>`，不要写 markdown 的 `*斜体*` / `**粗体**`**（原因见下）

### 为什么正文不能写 markdown 的 `*星号*`

这个站的正文基本是**整段整段的原生 HTML**（`<p>…</p>`、`<center>…`），
而 Markdown 有一条硬规矩：**HTML 块里面的内容不再当 Markdown 解析**。
只要一段以 `<p>` 开头，Goldmark 就整块原样输出，里面的 `*`、`` ` ``、`[链接]()`
全都不会生效，直接显示成字面符号。

老站（Bear Blog）那边能渲染出来，是因为它用的解析器和这儿不一样。
2026-09-12 清理过一次，全站正文里本来有 4 处这样的残留：

| 位置 | 原来 | 改成 |
| --- | --- | --- |
| `blog/sokuzai_cattest.md` | `*（虽然不全就是了）*` | `<i>（虽然不全就是了）</i>` |
| `niki_202602.md` | `**《想要飞的始祖小鸟》**` | `<strong>…</strong>` |
| `niki_202602.md` | `**德莱艾德（ドライエッド/Dryad）**` | `<strong>…</strong>` |

`description` 那行也一起清了（它进的是 `<meta name="description">`，本来就不解析 HTML，
所以直接把星号去掉）。**写新内容时记住这一点**：想要斜体/粗体就写标签。

正文里剩下的星号都是**故意**的，别当残留删掉：
`96*96`（图的尺寸）、`（攻击/防御）*威力`（公式）、`1.2*1.2=1.44`（伤害计算）。
`tobitaiaaken.md` 里那 6 个是 `<style>` 块里的 CSS 注释 `/* … */`。

### 博客 和 日记 是分开的两套东西

这一点和你原来的站点保持一致：

| | 博客 | 日记 |
| --- | --- | --- |
| 文件放在 | `content/blog/` | `content/niki/` |
| 网址 | `/blog/xxx/` | `/niki/niki_2026xx/` |
| 入口 | 导航栏「博客」、首页「最新博客」 | **只有** 导航页 `/navigator/` |
| 列表页 | `/blog/` 会列出 | 不生成列表页 |
| 首页最新列表 | 会 | 不会 |
| 侧边栏最新列表 | 会 | 不会 |
| RSS 订阅源 | 会 | 不会 |
| 上一篇 / 下一篇 | 会 | 不会 |
| 标签云 / 标签页 | 会 | 不会 |

「日记只能从导航页找到」是靠这几处配置一起实现的：

- `content/niki/_index.md` 的 `build.render: never` → 不生成 `/niki/` 列表页
- 同文件里的 `cascade.params.hideNav: true` → 日记页不渲染上下篇区块
- 日记不挂标签 → 不会出现在标签云和标签页里
- `layouts/rss.xml` → 首页订阅源只收 `blog` section

日记仍然会进 `sitemap.xml`（和 Bear Blog 原本的行为一致，方便搜索引擎收录）。
想改成「完全不进 sitemap」，在 `content/niki/` 里每篇加 `build.list: never` 即可。

### 写一篇博客文章

```powershell
hugo new content blog/文章名.md
```

套用 `archetypes/blog.md`。front matter 填 `title`（标题）、`date`（日期）、
`description`（摘要，列表页显示这句）、`tags`（标签，可选）。

### 写一篇日记

```powershell
hugo new content niki/niki_202610.md
```

套用 `archetypes/niki.md`。写完后记得三件事：

1. `title` 改成「2026年10月日记」这种格式
2. `date` 改成月份第一天（决定排序）
3. **不要打 `tags`** —— 一旦打了标签，日记就会出现在标签云和标签页里，
   等于开了导航页之外的第二个入口

**日历不用管了**（以前要手动往两个表格里加链接，见下面一节）。

#### 日历是自动生成的（2026-09-12 改）

日记页顶部那张表、导航页里每个月的表，**都不再写在正文里**，改成构建时生成：

| 位置 | 正文里写什么 | 谁负责渲染 |
| --- | --- | --- |
| 日记页 | `{{< niki-cal >}}` | `layouts/_shortcodes/niki-cal.html` |
| 导航页 | `{{< niki-cal-all >}}`（整页只有这一行） | `layouts/_shortcodes/niki-cal-all.html` |

两个短代码都调 `layouts/_partials/niki-days.html`，从**日记正文的日期锚点**推出
「哪些日子有内容」，再由 `layouts/_partials/niki-calendar.html` 画成表格。

**要做的只有一件事：写日记时给那天加个锚点。**

```html
<h2><span id="1005">10月 5日</span></h2>
```

`1005` = 月 + 日，四位数。加上去之后，日记页和导航页的日历里那一天**同时**变成链接。
跨日可以写在标题里：

```html
<h1> <span id="0901">9月 1日 ～ 9月 2日</span></h1>
```

这样 1 日和 2 日都会链到 `#0901`（括号里的补记说明不算，比如
「8月 2日（8月3日补记）」只会链 2 日 —— 这是照抄以前手写的习惯）。

**新开一个月**：照旧建 `content/niki/niki_YYYYMM.md`，正文里放
`<center>2026年 10月</center>` 和 `{{< niki-cal >}}`，
再写一句 `<center><b>神無月 稻穗结实 秋意渐浓</b></center>`（编辑器的模板会自动带上）。
导航页**一个字都不用改** —— `niki-cal-all` 会遍历所有日记页，自动多出那一块，
标语也是从这一行 `<b>` 里抓的。

> ⚠️ 新月份的 `date` 如果填的是**未来**的日期，Hugo 默认不会构建它，
> 导航页里也就不会出现。真要在月初之前先写，就把 `date` 往前提一天。

以前那个「同步导航页」的手工按钮已经停用了：`/api/nav/sync` 现在直接返回
「不需要同步」，编辑器里的那一页也变成了只读的一览表。再往 `navigator.md` 里写
静态表格只会让页面上出现两份日历。

### 「点阵宋体」小字（`pixelSongSmall`，默认开）

让**次级文字**（侧栏各挂件、文章 meta 行、列表摘要、页脚、标签、日历表格）
用回真正的**像素宋体**。这是全站最"2010"的一处，但有个硬性物理限制。

**原理：宋体内嵌的点阵只覆盖「12~17 设备像素」这一段。** 跟 CSS 字号无关，
只跟**最终渲染出来有多少设备像素**有关。实测（本机 Chrome，逐像素数灰边：

| CSS 字号 | 100% 缩放 | 125% | 150% | 200% |
| --- | --- | --- | --- | --- |
| 8px | 抗锯齿 | 抗锯齿 | **点阵** | **点阵** |
| 10px | 抗锯齿 | **点阵** | **点阵** | 抗锯齿 |
| 11px | 抗锯齿 | **点阵** | **点阵** | 抗锯齿 |
| 12px | **点阵** | **点阵** | 抗锯齿 | 抗锯齿 |
| 14px | **点阵** | 抗锯齿 | 抗锯齿 | 抗锯齿 |
| 16px | **点阵** | 抗锯齿 | 抗锯齿 | 抗锯齿 |

所以 CSS 里按 `min-resolution` 分了档，保证「字号 × 设备像素比」永远落在
12~17 之间，不管访客是 100% 还是 200% 缩放都能看到真点阵：

| 屏幕缩放 | 设备像素比 | 用的字号 | 实际设备像素 |
| --- | --- | --- | --- |
| 100% | 1.00 | 12px | 12.0 |
| 125% | 1.25 | 12px | 15.0 |
| 150%（站长这台） | 1.50 | 11px | 16.5 |
| 175% | 1.75 | 9px | 15.75 |
| 200% | 2.00 | 8px | 16.0 |
| ≥213% | ≥2.13 | 退回微软雅黑 | —— |

**验证结果**（站长这台 150% 缩放的机器，实测灰色中间调像素占比）：

| 取样 | 微软雅黑 | 宋体（本开关） |
| --- | --- | --- |
| 侧栏「关于站长」简介 | 76.9% 灰边、169 种灰阶 | **0.0% 灰边、0 种灰阶** |
| 一言引文 | —— | **0.0% 灰边、0 种灰阶** |
| 列表摘要 | —— | **0.0% 灰边、0 种灰阶** |
| 搜索提示 | —— | **0.0% 灰边、0 种灰阶** |

0% 灰边、0 种中间灰阶 = 整段文字只有「纯黑」和「底色」两种颜色，就是货真价实
的点阵渲染，一个模糊像素都没有。

**几条不能违反的规则**（不遵守就会退化成发虚的轮廓渲染）：

1. **带 `font-weight: bold` 的地方不能用宋体。** 合成加粗会破坏点阵 ——
   实测 11px 常规 0% 灰边、加粗 41.8%。所以 `#footer strong`、`.notice-label`
   被排除在外；日历表头 `.entry-content th` 则去掉了加粗，改用浅蓝底色区分。
2. **字号必须跟着 `--song-size` 走。** 别给换了宋体的元素单独写死字号，
   否则在那个 DPR 档位下就掉出窗口了。
3. **正文不换。** 11px 宋体在你屏幕上物理尺寸只有 6pt 左右（这块屏是 191 PPI，
   12~17 设备像素天生只有 2010 年 96 PPI 屏上的一半大），读长文太累。
4. **页面缩放（Ctrl +/-）会让某一档失效**，因为媒体查询只看设备像素比，
   看不到页面缩放。默认 100% 是好的。

> 顺带一个不影响观感的小事实：侧栏带下划线的链接会出现约 19% 的"混合色"
> 像素。查过了，**那是 1px 下划线落在半个设备像素上的抗锯齿，不是字糊了** ——
> 把 `text-decoration: none` 去掉再测，立刻回到只有 2 种颜色。

### 点阵字体模式（`pixelFont`，默认开）

全站换成点阵字体。开关键在 `hugo.toml`：`pixelFont` 改 `false` 一行就回到
微软雅黑；`pixelFontFile` 选哪一份字体：

| `pixelFontFile` | 字体 | 大小 | 来源 / 授权 |
| --- | --- | --- | --- |
| `"simsun12"`（当前） | SimSun12-Pixel | **58 KB** | 从系统宋体 12px 的**内嵌点阵**提取、再把每个点转成方块轮廓。`OS/2 fsType = 8`（Editable，允许嵌入）。字形就是 Windows 上最经典的 12px 宋体点阵 |
| `"vonwaon"` | VonwaonBitmap 12px | 94 KB | 独立像素字体，授权 `No rights reserved`，**无任何版权顾虑** |

两份都在 `static/fonts/`，都是按全站实际用到的 2212 个字符子集化后的 WOFF2
（原文件 11.8 MB / 1.5 MB）。

#### 日文假名单独走 MS Gothic（`pixelFontJa`，默认开）

日文不用上面那份，而是用从 `msgothic.ttc` 的 12ppem 点阵提取的
`msgothic12-jp-pixel.woff2`（**4.3 KB**）。分流靠 CSS **`unicode-range`**，
不需要给 HTML 加 `lang` 标记或额外 class：

```css
@font-face {
  font-family: 'MSGothic12JPPixel';
  unicode-range: U+301C, U+3040-30FF, U+FF61-FF9F;   /* 假名 + 〜 + 半角标点 */
}
```
字体栈写 `'MSGothic12JPPixel', 'SimSun12Pixel', SimSun, "宋体", monospace`，
MS Gothic 靠 `unicode-range` 把范围限死，只接管假名，汉字和标点继续走宋体。

浏览器实测（CDP `CSS.getPlatformFontsForNode`，这就是"到底用了哪个字体"的权威答案）：

| 元素 | 文字 | 实际字体 |
| --- | --- | --- |
| `.site-name` | 虹星的星虹巢｜**ほしのほしにじそう** | SimSun **7** + MS Gothic **9** |
| `.about-meta` | 昵称：**にじぼし** | SimSun **6** + MS Gothic **4** |
| `.footer-copy` | Copyright **©** 2010-2026 虹星 | SimSun **47**（不再掉回系统 NSimSun） |

几个坑：

1. **两份字体的度量不一样**，MS Gothic 是 1320/−216、宋体是 1280/−256。
   假名和汉字混在一行时行高会跳，所以 MS Gothic 那份用
   `ascent-override: 83.3333%; descent-override: 16.6667%; line-gap-override: 0%`
   把度量对齐到宋体。
2. **MS Gothic 的 12px 点阵里有 14 个假名是空的**
   （ゔゕゖ゗゘ ゙゚ ゟ ゠ ヷヸヹヺ ヿ —— 源字体本来就没给这些字点阵）。
   所以字体栈最后挂了系统 `SimSun` 兜底，避免它们掉到 `monospace`
   变成完全不同的字体。
3. **字符集要从构建产物（`public/`，HTML 实体已解码）里提取，不能从源码提取。**
   踩过：模板里写的是 `&copy;`，从源码提取只会拿到 `&copy;` 这 5 个 ASCII 字符，
   `©` 本身没进子集，页面上那个 © 就掉回系统 NSimSun 了。
   现在用 `mkcharset.py` 扫构建后的 HTML 再 `html.unescape` 一遍。
4. **`letter-spacing` 必须是整数个设备像素。** `.site-name` 原来的 `1px`
   在 150% 缩放下 = 1.5 设备像素，会让一半字形落在半个设备像素上、边缘发灰。
   点阵模式下 `.site-name` / `.header-stamp` 的 `letter-spacing` 已清成 `normal`。

> 宋体那份是用 `D:\DSHFiles\` 里的提取脚本做的，逐字形字节级比对过
> 28515 个字形、零差异。原始 `simsun.ttc` 的 12~17ppem 六档点阵里只取了 12px 一档。

#### emoji 走 Mona 的单色点阵（`emojiFont`，默认开）

不开的话 Windows 会用 **Segoe UI Emoji** 渲染 emoji：彩色、带抗锯齿、
尺寸也和正文对不上，是全站唯一不是点阵的地方。

现在换成 **Mona12Emoji**（Mona Font 的单色 emoji 子集，55 KB，
<https://github.com/MonadABXY/mona-font>，SIL OFL 1.1）：

- 它同样是 **12px 栅格**（`upem = 1200`，1 设计像素 = 正好 100 单位，
  1704 个字形、104012 个点全量核对：0 个出格点、0 段曲线），
  所以直接跟着 `--px` 走就行，不用另算字号。
- 用 `unicode-range` 只放开 emoji 区段（`U+1F000-1FAFF`、`U+2600` 起的那几段、
  `U+FE0F`、`U+200D` 等 40 段）。**没有 emoji 的页面完全不会下载这 55 KB。**
- 字体栈：`'MSGothic12JPPixel', 'SimSun12Pixel', 'Mona12Emoji', SimSun, "宋体", monospace`。
  Mona 排在两份宋体**后面**——范围里其实包含了 `©®™♀♂` 这些宋体点阵本来就有的字符，
  但宋体排在前面先命中，抢不走。
- 非点阵模式下（`pixelFont = false`），Mona 插在通用族 `sans-serif` **之前**。
  排在 `sans-serif` 后面等于永远轮不到 —— 通用族一定会命中系统字体，
  浏览器就直接用系统 emoji 了。

**为什么不直接写范围、还要管顺序**：两份来源不同的字体同时覆盖同一个码位时，
**字体栈里靠前的赢**。所以「谁先谁后」和「`unicode-range` 写多宽」要一起看。

**度量要覆盖**（和 MS Gothic 同理）：Mona 自己的 `hhea` 是 `1100 / -300`（em = 1200），
宋体点阵是 `1280 / -256`（em = 1536）。不覆盖的话一行里只要有 emoji，行高就会跳：

```css
ascent-override: 83.3333%; descent-override: 16.6667%; line-gap-override: 0%;
```

浏览器实测（CDP `CSS.getPlatformFontsForNode`）：

| 字符 | 实际字体 |
| --- | --- |
| 🍤 `U+1F364`（`niki_202608` 里 5 处） | **Mona12 Emoji x5** |
| ★ `U+2605`（顶部滚动公告） | SimSun12 Pixel x41（没被抢走） |
| ◇ `U+25C7` / ♂ `U+2642`（`self_intros`） | SimSun12 Pixel |
| ▽ `U+25BD`（首页 `(￣▽￣)ノ`） | SimSun12 Pixel |

逐像素实测：`emojiFont` 打开后，emoji 在 150% 缩放下按 16px CSS × 1.5 = **24 设备像素**
渲染（= 12 × 2），笔画正好 2 设备像素宽，**中间灰阶 0.0%**，和旁边宋体点阵汉字完全一致。

> 剩下的彩色描边（ClearType 次像素抗锯齿）是全站共性，不是 emoji 特有的：
> 版心左侧落在 372.5 CSS px 上，是半个像素，所以竖笔边缘会有红蓝彩边。
> 想彻底去掉只能上二值化滤镜（见文末「还没做的事」）。

**为什么必须"整倍缩放"**：两份字体都是「轮廓即像素方块」的矢量字体，
`upem` 分别是 1536（宋体，1 设计像素 = **正好 128 单位**）和 1200
（Vonwaon / Mona，1 设计像素 = **正好 100 单位**）。已全量核对：坐标全部落在网格上，
**没有一条曲线，全是直线**。所以锐利的条件是

```
字号(CSS px) × devicePixelRatio = 12 的整数倍
```

`head.html` 里有一段内联脚本，在首屏渲染之前按当前 DPR 算出字号：

| 屏幕缩放 | DPR | 基础字号 | 实际设备像素 | 标题 | 大标题 |
| --- | --- | --- | --- | --- | --- |
| 100% | 1.00 | 12px | 12（=12×1） | 24px | 36px |
| 150% | 1.50 | **16px** | 24（=12×2） | 24px | 32px |
| 200% | 2.00 | 12px | 24（=12×2） | 18px | 24px |

页面缩放（Ctrl +/-）会改变 `devicePixelRatio`，脚本监听到变化后自动重算。

**三条必须遵守的规则，破坏了就会糊：**

1. **字号不能写死。** 必须取自 `var(--px)` / `var(--px-lg)` / `var(--px-xl)` /
   `var(--px-sm)`。写死 13px 这种数字 → 19.5 设备像素 → 掉出整数倍，方块立刻糊。
2. **这些规则必须带 `!important`。** 基础样式里有 `#notice`、`#gotop`、
   `#navbar .nav li a` 这类 ID 选择器写死了 12px / 13px，优先级比通配规则高，
   不加 `!important` 它们会停在 18 / 19.5 设备像素上（这个坑踩过，全站就那三处糊）。
3. **不能用 `text-shadow`。** 带模糊的描边会把方块边缘糊成灰的。所以点阵模式下
   全站 `text-shadow` 被清掉了，只留 LED 时钟/计数器的绿色辉光和挂件标题条的描边
   （那两个是故意留的原字体）。

另外**不能加粗**：这两份字体都没有粗体，浏览器合成的假粗体会把方块糊掉
（实测中间灰像素占比从 39% 涨到 52%）。所以全站 `font-weight` 统一压成
`normal`，层级**改用字号**表达，页脚的 `<strong>` 改用黄底红字。

#### 正文里的斜体和粗体（2026-09-12）

点阵模式下 `font-weight` 被压成 `normal`，后果是正文里的 `<b>` / `<strong>`
**完全看不出来**（实测 computed `font-weight` 就是 400，和普通 `<span>` 一模一样）。
`<i>` / `<em>` 倒是正常 —— 浏览器会把字形斜过来（合成斜体）。

所以正文的 `<b>` / `<strong>` 用一个「假粗体」补上：

```css
html.pxfont .entry-content b,
html.pxfont .entry-content strong {
  text-shadow: var(--devpx, 1px) 0 0 currentColor !important;
}
```

`--devpx` = **一个设备像素等于多少 CSS px**（= 1/dpr），由 `head.html` 里那段
内联脚本算出来。原理是**把同一个字形往右错开整一个设备像素再画一遍**：
两遍都是像素对齐的，不会产生半像素灰边，笔画稳定地加粗一个设备像素。

实测横切游程（同一段文字）：

| | 100% 缩放 | 150% 缩放 |
| --- | --- | --- |
| 普通 | `2px×55 3px×6 4px×12 …` | `2px×170 4px×12 6px×10 …` |
| 粗体 | `3px×39 4px×6 5px×10 …` | `3px×170 5px×12 7px×10 …` |

150% 那两行是**每一段游程都正好 +1 设备像素**（条纹数量完全一样），
方块仍然是硬的。

> ⚠️ **偏移量不能写死 `1px`**：150% 缩放下 1 CSS px = 1.5 设备像素，
> 又会落在半个像素上把边缘糊掉。必须走 `--devpx`。

`<i>` 就不动它了：斜体本来就是「把字形斜过来」，斜边天然不在像素网格上，
边缘会比正文软一点（实测彩色描边从 72% 到 77%），但仍然是清楚的斜体。
真想让斜体也硬边，只能改成「不倾斜 + 换个颜色」，那是另一套观感了。

不改字体的零件：侧栏挂件标题条（蓝底白字，靠加粗）、LED 时钟、访客计数器
数字、88×31 小按钮 —— 它们靠加粗/等宽表达，换成点阵只会更糟。

> **本地预览一定要用 `http://localhost:1314/BlogStand/`**（Hugo 自己打印的
> 那个地址），**不要用 `127.0.0.1`**。字体是 CORS 模式加载的，而
> `canonifyURLs = true` 会把样式表地址写成 `localhost`，
> 用 `127.0.0.1` 打开时页面和样式表就变成两个主机名，字体请求会被浏览器
> 直接拒掉（表现是"字体没生效"，很容易误判成 CSS 写错了）。

**已知的局限（实测，不是 bug）**：Chrome 栅格化这份矢量轮廓时仍会带上
抗锯齿 —— 竖排的方块是严丝合缝的、一个灰行都没有，但横排大约每 6 个设计
像素会漂半个设备像素，于是边缘带一点灰和 LCD 彩边。想要 100% 硬边，得再叠
一层二值化滤镜：

```css
html.pxfont .entry-content p { filter: url(#pxbin); }
```

（`feComponentTransfer` + `type="discrete" tableValues="0 1"`，实测能把中间
灰像素压到 0%。代价是滤镜作用范围内所有颜色会被一起拉成纯色，浅色底纹会
变纯白，所以只适合套在纯文字元素上。）

**做这套风格时踩到的两个坑**（注释里也写了，别再踩）：

1. **背景图必须是 PNG，不能用 GIF。** 这台机器上 `System.Drawing` 存 GIF
   会把调色板写坏 —— 实测把 `#e3eefa` 存成了 `#CCFFCC` / `#FFD5FF` 这种
   青一块粉一块的噪声，页面底纹会变成一片麻点（看着像"随机噪点纹理"，
   其实图是坏的）。PNG 存下来是精确的。
2. **CSS 里的图片路径必须用 `absURL`，不能用 `relURL`。** 站点在
   `/BlogStand/` 这个子路径下，而 `relURL` 在 CSS 里拿不到这个前缀，
   会渲染成 `/images/...`，直接 404。HTML 模板里 `relURL` 是好的，
   只有这个被 `ExecuteAsTemplate` 处理的 CSS 文件有这个问题。

### 侧栏「一言」用的句子

句子**不是**从外部一言 API 抓的，而是从站长自己写的小说里摘的，
全部存在 `data/hitokoto.toml` 的 `quotes` 数组里，出处统一署笔名 **平铃**。

小说的原站在这里：<https://boxofhoshi.blogspot.com/>（星虹箱）

加句子时请守住这四条，否则会破坏「都是原句」这一点：

1. **必须是原文逐字子串**，一个字、一个标点都不能改。
2. **只能收在句子边界上**（原文本身就是 `。！？…` 结尾）。
   ⚠️ 不能把原文的逗号改成句号来"造"一个结尾——那就不算原句了。
3. 长度控制在一到两行。侧栏宽 300px、字号 12.5px，**约每行 22 字**，
   所以 **12~45 字**最合适。
4. **不收 R18 / 露骨 / 暴力血腥**的内容。

> 2026-09-11 初版的做法：先用 6 个并行子代理从 6 部作品里摘了 76 条候选，

`{{ ... | jsonify }}` 的结果会被再包一层引号变成字符串，
必须写成 `{{ ... | jsonify | safeJS }}`。

## 五、关于图片

`static/images/migrated/` 里是从旧站搬过来的 92 张图，**已经是原图**（2026-09-11 换过）。
正文引用的是本地路径 `/images/migrated/xxx.png`，不依赖任何外部图床。

### 图片是怎么来的（以及踩过的坑）

旧站的图放在 `i.ibb.co`（ImgBB）。这个图床有个**按 Referer 区别对待**的行为：

| 请求时的 Referer | 拿到的图 |
| --- | --- |
| `https://ibb.co/` 或 `https://imgbb.com/` | **原图** |
| 其它任何 Referer，或没有 Referer | **180×180 缩略图** |

第一次迁移时脚本没带 Referer，所以 92 张全部拿到了 180×180 缩略图，糊得很明显
（原图本来就小于 180 的甚至被**放大**过，最糟）。

> ⚠️ 关键点：决定因素是 **Referer**，**不是 User-Agent**。
> 用浏览器 UA、加 `Accept`、加 `Referer: 老站域名` 全都没有用，只有 Referer 是
> imgbb 自家域名时才返回原图。这一点当初猜错过一次，别再踩。

### 想重新拉一遍原图

1. 从老站 sitemap 取全部页面：<https://hoshi-rainbowsou.bearblog.dev/sitemap.xml>（现 17 个）
2. 抓每个页面里所有 `i.ibb.co` 链接（注意：`&quot;` 之类的 HTML 实体会混进正则，要清掉）
3. **下载时必须带 `Referer: https://ibb.co/`**，否则只会拿到缩略图
4. 老站有 Cloudflare 防护，脚本连续请求会 403；每次请求间隔 **4 秒以上**，失败要退避重试

### 优化策略

正文列宽是 634px（`.entry-content` 的 `max-width: 100%` 就是相对它算的），所以：

- 长边超过 **1280px**（630 的 2 倍，够视网膜屏）的缩到 1280，JPEG 质量 85
- 长边本来就不超 1280 的**原样保留**，不重新编码，避免二次损失
- **动图（GIF）不处理**，避免破坏动画

当前 92 张合计约 35 MB。其中 `Bounce-Game.gif` 单张就 11.47 MB（649×473、231 帧动图），
是 `niki_202608` 那页偏重的主因；想再瘦身优先动它。

另外所有 `<img>` 都带 `loading="lazy"`（老站原本就有，第一次迁移时丢了 72 个，已补回），
首屏只加载可视区里的图。

### 图片戳出白色卡片（2026-09-12 修）

症状：日记页里的图会从白色卡片右边**戳出去约 19px**，压在版心底纹上，紧挨着侧栏。

原因不是"图片太宽"，是两条 CSS 叠加起来多算了 30px（用 CDP 逐元素量出来的）：

| 项 | 数值 | 说明 |
| --- | --- | --- |
| 正文列宽 | 634px | `#content` 656 − 卡片边框 2 − `.box-body` 内衬 20 |
| `max-width: 100%` 的算法 | +6px | 全局 `box-sizing: content-box`，所以 100% 只管**内容盒**；再加 `padding: 2px`×2 和 `border: 1px`×2，图片实际渲染成 **640px** |
| `.entry-content p` 的 `text-indent: 2em` | +24px | 段首那张图被再往右推 24px |

640 + 24 = 664，减掉 10px 内衬 —— 于是右边缘落在 1036，而白色卡片右边缘在 1018，**戳出 19px**。
（`<center>` 里的图因为不吃缩进、又左右对称，只多出 3px，基本看不出来，所以当时觉得"有些图"才这样。）

修法两条，都在 `assets/css/retro.css`：

```css
.entry-content img { box-sizing: border-box; }        /* 让 max-width 把衬边算进去 */
.entry-content p:has(> img:first-child) { text-indent: 0; }  /* 段首是图就不缩进 */
```

用 `:has()` 而不是给 `img` 加 `display: block`，是因为后者会把 `<p><img><img></p>`
这种并排的图拆成两行。`text-indent` 只作用于**首行**，所以 `<p><br><img>` 这类
图本来就在第二行、不吃缩进，不用管。

改完实测：全部 44 个页面（含 21 个别名）**戳出 0 处、被裁 0 处**，
图片右边缘停在 1006.5（卡片 1017.5），150% 缩放下同样是 −11px。

> ⚠️ 顺带修的另一处：首页欢迎区（`.welcome-inner`）不在 `.entry-content` 里，
> 拿不到那条 `img` 规则，而它外层是 `overflow: hidden`。所以那里的图一旦超宽是
> **被切掉**而不是戳出去，两种都难看 —— 已补 `.welcome-inner img { max-width: 100% }`。

## 六、日期、字数与阅读时间

### 字数和阅读时间为什么不能用 Hugo 自带的

Hugo 的 `.WordCount` 是**按空白分词**算的，中文没有空格，整段中文只算一个词。
实测偏差：

| 页面 | `.WordCount` | 实际字符数 | 差 |
| --- | --- | --- | --- |
| niki_202607 | 176 | 7,994 | 45× |
| ihsobijin2006 | 21 | 3,842 | **183×** |
| blog/tabideru_20260901 | 48 | 2,494 | 52× |

`.ReadingTime` 又是 词数 ÷ 213，所以全站都显示「阅读 1 分钟」。

所以改用 `layouts/_partials/stats.html`：

- **字数** = 正文 `plainify` 去掉 HTML 标签后，再删掉所有空白的字符数
- **阅读时间** = 字数 ÷ `readingSpeed`（`hugo.toml`，默认 400 字/分钟）

模板里用法：`{{ $st := partial "stats.html" . }}`，然后 `$st.Chars` / `$st.Minutes`。
`post-meta.html`、`home.html`、`list.html` 都用它。

### 「发布于」这些日期是哪来的

内容里的日期**不是**旧站直接给的，来源分三类，改之前先看清楚：

| 页面 | 日期来源 |
| --- | --- |
| blog 的 3 篇（tabideru / sokuzai_cattest / sokuzai-collected） | 旧站 RSS / Atom / `/blog/` 列表页的**精确时间戳**，UTC 换算成 +8 |
| niki_202602 ~ 202609（8 个月记） | `date` = **当月第一条日记的日期**，`lastmod` = **当月最后一条日记的日期**（从正文的 `<span id="MMDD">` 锚点取） |
| gallery / navigator / tobitaiaaken / ihsobijin2006 / self_intros | 旧站 `sitemap.xml` 的 **`lastmod`** |

> ⚠️ 旧站的日记页和其他页面在 Bear Blog 里是 **page**，page **本身没有发布日期**
> （页面里没有日期文本，`<meta>` 和 JSON-LD 里也没有 `datePublished`）。
> 唯一可用的真实数据就是 sitemap 的 `lastmod`（= 最后修改日期）。
> 所以上面第三类的日期语义是「最后修改」，不是「发布」——想改就直接编辑
> 对应 .md 的 front matter。

旧站的这两份数据仍在，需要时可以重新取：

- sitemap：<https://hoshi-rainbowsou.bearblog.dev/sitemap.xml>（含全部 17 页 lastmod）
- `/blog/` 列表页：<https://hoshi-rainbowsou.bearblog.dev/blog/>（3 篇博客的精确 `<time datetime>`）
- RSS：<https://hoshi-rainbowsou.bearblog.dev/feed/?type=rss>

### 时区

`hugo.toml` 里设了 `timeZone = "Asia/Shanghai"`。

注意 Hugo 的 `.Date.Format` 是**按时间戳自身的时区**渲染的，`timeZone` 配置不改这一点。
所以带时间的 front matter 要写成 **+08:00 偏移**，例如：

```yaml
date: 2026-02-15T03:42:00+08:00   # = 旧站的 2026-02-14T19:42Z
```

写成 `...T19:42:00Z` 的话页面上就会显示 19:42（比实际发帖时间早 8 小时）。

## 七、部署到 GitHub Pages

### 1. 建仓库

| 仓库名 | 站点地址 |
| --- | --- |
| `你的用户名.github.io` | `https://你的用户名.github.io/`（**推荐**） |

### 2. 改 `hugo.toml` 里的地址

```toml
baseURL = "https://你的用户名.github.io/"
```

> 子路径仓库记得带目录名：`https://你的用户名.github.io/home/`
> **填错会导致 CSS 和图片全部 404。**

### 3. 开启 Actions 发布

仓库 → **Settings** → **Pages** → **Build and deployment** → **Source** 选 **GitHub Actions**

### 4. 推送

```powershell
git init
git add .
git commit -m "first commit"
git branch -M main
git remote add origin https://github.com/你的用户名/你的仓库名.git
git push -u origin main
```

推送后 `.github/workflows/hugo.yml` 会自动构建部署，约一分钟上线。
之后每次 `git push` 网站自动更新。
